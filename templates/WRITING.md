# 写作约定

这个仓库的读者是「学过计算机基础、但没系统学过机器学习系统」的人：可能是在准备面试的工程师，也可能是刚进组的同学。
写的时候想象自己在给一位聪明但不熟悉这块的同事讲：先让他知道为什么要关心这件事，再给推导和数字，最后告诉他哪里容易错。

## 内容上的底线

- **数字只能来自实测或可复算的推导。** 改写时不改任何数字、单位和结论；不加仓库里没有依据的新数字、新事实或新经历。
- **保留「不能推出的结论」。** 每个实验的局限、口径和「这里没有验证」的说明都要留着，这是材料可信的原因。
- **链接和标题要稳。** 其他文件会用 `文件#标题` 链接过来，改标题前先全仓搜一遍引用；笔记的固定小节标题（见 `notes/check_notes.py`）不要改。
- **代码块和公式块不改内容。** 可以在块前后补一句说明它在干什么。

## 写法

**先讲为什么，再讲是什么。** 每一节开头用一两句话交代这节要回答的问题，或者不懂它会在哪里吃亏。
例如讲 roofline 之前，先说「同样一个 kernel，为什么换个 batch 就快了十倍」。

**一句话只说一件事。** 一句里塞了三个以上的数字或术语，就拆开。数字是用来支撑观点的：
正文里只留能说明问题的那一两个，成批的数字放进表格。

**术语第一次出现时顺手解释。** 比如「算术强度（每从显存读一个字节，做多少次浮点运算）」。英文术语保留，
因为面试和论文里都用英文，但第一次要让读者知道它指什么。

**把因果写出来。** 多用「因为」「所以」「但是」「换句话说」把句子连起来，让读者看到推理的过程。
少用箭头链（`A → B → C`）、斜杠并列（`spin/sleep/spawn`）和电报式短语来代替完整的句子；表格和公式里可以用。

**有经验就写经验，没有就别编。** 实验里真实发生过的事（第一版测错了、某个假设被数据推翻了）用第一人称讲出来，
这是最有价值的部分。没发生过的「我当时想」不要写。

**列表只用于真正并列的东西。** 解释和推理用段落；三五个并列的选项、步骤或检查项才用列表；数字对比用表格。
不要为了显得有条理把一段话切成碎片。

**加粗要少。** 一屏里最多一两处，留给读者真的不能错过的那句话。

## 避免的说法

这些写法会让文字显得空泛或像模板，能删就删，能换成具体内容就换：

| 少用 | 改成 |
| --- | --- |
| 「值得注意的是」「需要指出的是」「关键在于」 | 直接说那件事 |
| 「本质上」「从根本上说」 | 说出具体机制 |
| 「总而言之」「综上所述」开头的总结段 | 小结里只写读者该带走的两三点 |
| 处处「不是 A，而是 B」 | 只在真的要纠正一个常见误解时用 |
| 凑成三点的排比、「首先 / 其次 / 最后」 | 有几点写几点 |
| 「显著提升」「极大地」等形容词 | 给出数字，或者不说 |
| 每段都以一句金句收尾 | 说完就停 |

## 每类材料的重点

- **笔记**（`notes/`）：按固定小节写，但各节分工要清楚。「核心概念」讲直觉和机制；「关键推导」一步一步推；
  「高频问题」是短问短答；「面试追问链」是由浅入深的连续追问；「自测题」是要动手算的题。同一个问题不要在三处重复出现。
- **实验 README**（`solutions/`）：先用一段话说清这个实验要回答什么问题、结论是什么，再讲怎么跑、每张图看什么。
  每张图下面写「这张图说明了什么」，而不是重复图里的数字。
- **面试材料**（`interview/`）：写成可以直接说出口的话。一个回答先给结论，再给一个支撑的数字或推导，最后点出常见的错答。
- **报告**（`reports/`）：是给人从头读到尾的文章。每节开头交代动机，图表前后有过渡，结论框里只放一两句真正的结论。
